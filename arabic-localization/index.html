In-game testing

Arabic for games that shipped without it

Homura Hime and What Remains of Edith Finch, in Arabic.

Neither game supports Arabic, and neither engine draws it correctly on its own. Arabic letters join and change shape, sentences run right to left, and diacritics sit above and below their letters. These games’ text systems assume none of that. For Homura Hime I built the whole pipeline, from pulling every string out of the game to a plugin that draws Arabic in its menus and dialogue. For Edith Finch, where most words on screen are 3D models, I built Arabic letter models in the game’s own format and played the whole game through in Arabic.

Project lead: scope, glossary and style decisions, and every in-game test. AI agents drafted the Arabic and assisted with engineering.

Overview

Four problems at once.

Homura Hime is an action game built in Unity 6. Its text lives in three different places, its fonts contain no Arabic letters, and its text components lay out every line from left to right. Adding Arabic meant solving four problems together: find every string, translate it consistently, check Arabic grammar at the scale of eleven thousand lines, and make the engine draw it correctly.

I set the ground rules before any code was written, and they shaped every technical decision:

  • Never change a game file. The patch only adds files, and removing it restores the game exactly.
  • Never strip diacritics. Arabic tashkeel carries meaning, so it is kept exactly as written.
  • Every step is reproducible. Scripts are committed, backups come before overwrites, and source text is preserved byte for byte.
  • No claim without evidence. A result counts as “working in game” only after I have seen it in the game myself.

Finding the text

The first plan was for the wrong engine.

The first brief assumed Unreal Engine tools, because that is what Edith Finch needed. Before building anything, I profiled the game’s files. Homura Hime is Unity 6000.0.28f1 on the Mono backend, with unencrypted Addressables bundles, so the plan was rebuilt from scratch. Checking the engine first is now step one on every project.

The text turned out to live in three places:

  • 19 Unity Localization tables, each in four languages. Their key names sit in shared data bundles eight folders deep.
  • A settings spreadsheet, HomuraHime_UILocalization.xlsx, with 126 rows.
  • The dialogue: one Utage scenario “book” inside sharedassets1.assets, with 187 sheets and 15,601 rows. CSV files that looked like the script were leftovers from the publisher.

The extractor pulled out 2,167 interface rows and 8,755 lines of dialogue, plus 130 speaker names, and checked every string byte for byte against the raw table data. It also catalogued what must survive translation untouched: input icons like [SHOOT] and [L3], TextMeshPro tags, and titles in literal angle brackets, like <Yudachi Evening Post>, that look like tags but are text.

The pipeline

From game files to Arabic on screen.

Each batch is a JSON file with exactly nine fields per row. The translator may change only three of them: the Arabic text, notes, and a status that moves from needs translation to translated to reviewed. Batches are created once and never overwritten, so nothing a translator delivers can be lost to a re-run.

Making Arabic render

Three tests, then the real thing.

Unity’s text components don’t shape Arabic and don’t lay out right to left. I tested each idea inside the game with a small test plugin before building the real one.

  1. 1

    Render test 1 · 29 September

    The obvious switch made things worse

    TextMeshPro has a built-in right-to-left setting. It reversed digits, turning 123 into 321, and would reverse any English too. The game’s log revealed something more important: TextMeshPro barely matters here. Almost all text goes through Unity’s older UI.Text and the Utage dialogue engine.

  2. 2

    Render test 2 · 29 September

    Letters joined, but lines started on the wrong side

    The plugin now pre-shapes the text into Arabic presentation forms, in visual order, with each diacritic placed just before its letter. Arabic appeared joined, in the right order, with diacritics on the right letters, in the game’s own fonts through Windows font fallback. But every line still started from the left. My note after the test: the lines are written from the wrong side.

  3. 3

    Render test 3 · 29 September

    The game breaks the lines; the plugin mirrors them

    Instead of guessing line widths, the plugin lets the game wrap each paragraph with its real font and box size, then mirrors every line and right-aligns it. Dialogue now types in from the right, paragraphs wrap in the right order, and input icons like [L3] stay intact. One thing broke: right-aligned menu labels slid out of their red bars. That set the rule that menus keep the game’s own layout.

    The real plugin is built from all 400 passing batches and verified offline. I played the first three areas of the game in Arabic, about two hours of play.

Problems and fixes

What got in the way.

Machine-drafted Arabic needs grammar checks at scale

Problem

Nobody can proofread eleven thousand lines line by line before every build. Arabic adds traps English doesn’t have: pronouns and adjectives must agree in gender with what they refer to, and a missing or extra pronoun changes the meaning.

What I did

I specified a grammar gate that runs on every batch before a person sees it. Built on CAMeL Tools’ Arabic morphology, it checks pronoun references, gender agreement, redundant and missing pronouns, numbers, tags, tokens and line breaks. It reports an error only with strong evidence, and it flags problems without ever fixing them.

400 of 403 batches pass with zero errors. The other three hold only debug strings.

The checker raised false alarms

Problem

On real deliveries the checker flagged correct Arabic. The word الآن (“now”) contains آن, a character’s name, so it was read as a mention of that character. Some nouns, like الأرض (“the earth”), are feminine without looking feminine.

What I did

Every false alarm follows the same procedure: write a test case from the real line, show it fails on the old checker, fix the checker, then re-run every delivered batch. Names now match whole words only, and lexically feminine nouns are handled.

65 pronoun cases and 38 number cases, each one from a real line.

The game’s fonts have no Arabic letters

Problem

The game ships Roboto and Japanese and Chinese fonts. None of them contains a single Arabic glyph.

What I did

Render tests showed that Unity falls back to the operating system’s fonts for missing characters, so Arabic draws on Windows through fonts like Arial and Segoe UI. That works today. Bundling an open-licensed Arabic font, such as Noto Naskh Arabic or Amiri, is the remaining decision.

Arabic draws in the game’s own text components with no font replaced.

Two languages had to agree on every line

Problem

The line-mirroring logic exists twice: in Python, where the build is checked, and in C#, inside the plugin. If the two ever disagree, a line that passed every offline check could still render wrong in the game.

What I did

I added a parity test that runs the same cases through both implementations and compares the output, including diacritics, lam-alef ligatures, digits, Latin text and brackets.

493 of 493 cases match on the real translated data.

Spreadsheets quietly destroy data

Problem

String IDs like 43156479604867072 are too large for Excel or JavaScript numbers, which round them silently. Saving the glossary as a plain CSV in Excel wipes out Arabic and Chinese text.

What I did

IDs are always stored as text, never as numbers. The glossary must be saved as “CSV UTF-8”, and that rule is written into the project instructions for everyone who edits it.

No lost IDs and no corrupted Arabic between the translator, the tools and the build.

Installing a patch without touching the game

Problem

The easy route replaces the game’s data bundles, which breaks on every update and is hard to undo. I ruled that out from the start.

What I did

The patch is a BepInEx plugin that only adds files. The installer refuses to overwrite anything, writes a record of every file it adds, and on removal deletes exactly those files and re-checks the game’s hashes. The BepInEx log contains the PC’s hardware names, so it is kept out of Git.

12 of 12 install and removal tests pass on a mock game folder.

What Remains of Edith Finch

A game whose words are 3D models.

Edith Finch was the first game I localized into Arabic. It runs on an early version of Unreal Engine 4 and tells its story in words placed in the world, and most of the family’s stories have their own handwriting font. Those words aren’t text the engine lays out. Each letter is a small 3D model, and the game has no translation files to edit.

The ground rules were the same as for Homura Hime: game files stay read-only, and nothing in the game’s code changes. Everything ships in one extra archive, FinchGame_Arabic_P.pak, which the engine loads on top of the original. Removing it restores the game. I have played the whole game through in Arabic, from start to finish.

The game has no translation files

Problem

Unreal games usually keep their text in .locres files, and my first plan was to rebuild those. Edith Finch has none. Its dialogue sits in 12 tables with 1,286 English rows, so I changed three strings there as a test. The menu stayed in English.

What I did

I scanned all 20,261 of the game’s assets and found the text the player sees baked into the maps. Every piece of text owns a saved layout for each language, holding the string, a position for every letter and the font that draws it. So the patch rewrites the English layouts themselves: 1,093 of them, in 118 maps.

A test patch that drew “TEST” in the main menu proved a removable archive can replace a map.

The words are 3D models, not text

Problem

Each of the game’s mesh fonts maps one character to one small cooked 3D model. None of them has a single Arabic letter, so real Arabic characters drew as boxes.

What I did

First I proved how the lookup works: pointing Arabic characters at existing Latin models drew “A B C D”. Then I built new letter models in the game’s own cooked format, with three levels of detail each, using the shipped letter “P” as the template. They are added to the fonts at private-use code points. Font entries point to their model by a plain path, so adding letters needed no changes to the package’s import table.

On 26 September the main menu showed العب (“Play”) right-aligned on the English baseline, joined, with its dot below.

One shape per letter can’t spell Arabic

Problem

My first version gave each Arabic character one model. But Arabic letters change shape with their position in a word, and a font entry holds only one shape. It failed on the first word that needed one letter in two forms, الخيارات (“Options”). Arabic presentation forms, the usual shortcut, don’t cover the marks or the font’s ligatures either.

What I did

Each line is now shaped first with a real Arabic font, Noto Naskh Arabic, which joins the letters, places the marks and orders the words right to left. The shaped line is cut into clusters, each cluster becomes its own model at its own code point, and the layout gets new letter positions. A cluster is reused wherever the same shape appears at the same size.

The latest build rewrites 1,035 layouts in 93 maps with 4,691 Arabic glyph models across 9 of the game’s fonts.

Diacritics need room the English lines don’t have

Problem

Tashkeel sits above and below the letters, so fully vocalized Arabic stands taller than English. From the files I estimated a menu line pitch of 121 units and a 1.1× zoom on the selected item.

What I did

I built a test menu that uses every mark (fatha, damma, kasra, sukun, shadda with a vowel, tanween, hamza with kasra), 46 models in all, and measured it in the game: a pitch of 130 units and a 1.18× zoom. Story lines now get a taller pitch where Arabic needs it, and one-line menu items shrink to fit instead of wrapping.

Every mark sat on its own letter, even on the highlighted item. Four marks touched the line below by about a pixel.

A file format modern tools can’t open

Problem

The packages use an early Unreal Engine 4 format, from around version 4.9 or 4.10. Current UAsset tools can’t read them at all, and the main archive is compressed with Oodle.

What I did

The project reads and writes the packages itself, and each writer had to reproduce the original files byte for byte before I trusted it. Some packages carry an extra version table that shifts the header, which broke my first scan on 21 of them until the parser handled it. Decompression uses the game’s own Oodle library, loaded in place and never copied.

All 21,743 archive entries read with verified hashes, and four of the game’s own letter models re-encode byte for byte.

Words in the credits ran into each other

Problem

Playing a full build, I saw words in the credits overlapping. I had no screenshot of it, so the cause had to be found offline.

What I did

Analysis found three causes: credit blocks in the pause menu ran into the next block, dots under one line touched the line below, and Latin names were drawn 27% larger than in English. Blocks are now held to their English footprint, lines keep an even clearance, and names use the English letter height. A neighbour check now places every text’s real outlines at its position in the world and compares them.

Confirmed in the game during my full play-through.

The Arabic uses Noto Naskh Arabic for most of the game. For Edie’s letter and pages I chose Aref Ruqaa, for a slightly older, handwritten feel. The title logo’s three lines step down to the right in English, so in Arabic I mirrored the steps.

The patch installs and uninstalls with one click, through batch files driving a PowerShell script, with instructions in Arabic and English. It looks for Steam, Epic Games and GOG installs, checks its own file before and after copying, warns if the game is a different version from the one it was built for, and refuses to install over an older test patch.

The most useful thing Edith Finch taught me was not a tool. It was the habit of checking how a game is built before planning anything, which is exactly what saved Homura Hime from a pipeline built for the wrong engine.

Skills

What this project took.

Unity internals

Asset bundles, Addressables, Unity Localization tables and the Utage dialogue engine, read with UnityPy.

Runtime patching in C#

BepInEx plugins and Harmony patches on the engine’s text components, with reflection where APIs are private.

Arabic text engineering

Shaping, presentation forms, bidirectional order, diacritics and line mirroring.

Language tooling

Grammar checks built on CAMeL Tools morphology for agreement and pronoun errors.

Data pipelines

Batching, import, validation, sign-offs and reproducible builds from thousands of rows.

Test design

A regression case for every false alarm, and parity tests across two languages.

Unreal Engine

Reading and writing UE4 packages without engine tools, cooked 3D mesh fonts, and priority .pak patches.

Project leadership

Ground rules, a decision log, and an evidence ledger that separates “seen in game” from “verified offline”.
