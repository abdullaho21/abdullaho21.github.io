Gravity Rush Remastered, read from its own data

Decoding a PS4 game’s formats and redrawing them natively in C++.

Gravity Rush Remastered only runs on PlayStation. My long-term goal is to understand it well enough to run its content natively on a PC. This is a private study of the PS4 release’s data: I mapped its archives and scripts, decoded its model, skeleton, animation and scene formats, and wrote C++ readers and a Direct3D renderer that draw the opening area from the original files.

Overview

A game with no documentation at all.

Nothing about Gravity Rush’s file formats is public. There is no SDK, no format specification and no source. Everything on this page was worked out from the bytes: how the archives are laid out, how a model stores its vertices, how a skeleton is wired, how animation is compressed, and how a scene places its objects.

The work moves in small, provable steps. Each step starts with a hypothesis about a format, turns it into a parser, and only counts once the parser’s output closes exactly: every bit accounted for, every transform consistent, every result matching a sealed reference digest. When an idea fails that test, it is recorded as failed and never forced to fit.

Ground rules

Careful by design.

Reverse engineering a commercial game carries legal and ethical weight, so the limits came first and every milestone was checked against them:

  • Read-only game files. Every inspection verifies the SHA-256 of all 14 game inputs before and after; any change rejects the result.
  • Nothing leaves memory. Decoded textures, meshes and animations stay in RAM. No exports, no caches, no screenshots of game assets.
  • Nothing runs. Extracted scripts and binaries are read, never executed. The renderer is original C++.
  • No DRM work. No decryption, no keys, nothing uploaded or released.

An honest label. This is a private study informed directly by the game’s data. It is not a clean-room reimplementation, and none of it has been published.

    Catalogued all five archives: 21,897 named entries and 534,510 data blocks, about 34 GB once decoded, with every block and entry size matching its manifest.     A native C++ and Direct3D prototype drew its first original model from the GX64 data: the apple from the opening scene, 2,180 vertices and 3,918 triangles, with its texture coordinates and material links proven.

  3. 5

Problems and fixes

What got in the way.

The game’s code is encrypted

Problem

The game’s executable is an encrypted PS4 binary. Decrypting it would mean DRM work, which I ruled out from the start, so disassemblers like Ghidra had nothing to read.

What I did

I started from the data instead. The 1,204 Lua scripts are readable text, and the 681 system functions the game imports can be named using the open-source shadPS4 emulator’s tables. Together they give a first map of how the scripts call into the engine.

A working picture of the engine from 61,023 call sites, without touching its code.

Animation hidden in packed bitstreams

Problem

The 40AE animation format is undocumented. It packs each frame into variable-length bitstreams, and stores rotations with one axis left out to save space.

What I did

I decoded it field by field and only accepted a reading when every bit count, value range and padding byte added up exactly. The missing rotation axis is rebuilt from the other three, and the first pose of each clip is compared against the skeleton’s own rest pose.

Four original clips play, with rotation error below 1.4 × 10−7.

A hypothesis that turned out wrong

Problem

An early reading of the skin palette mapped entry 41 to scene node 54. Static rendering never used that mapping, so nothing failed and the mistake sat unnoticed.

What I did

When skinning was built, the proof showed entry 41 actually points to node 40, counting from one. I corrected it, marked the old record as historical, and made every rig pass a closure check before any mesh could use it.

All 169 inverse bind matrices now close within 10−5.

A field that wouldn’t give up its meaning

Problem

One field in the scene records looked like it selected which mesh to draw. Building on that guess would have been easy, and wrong if the guess was wrong.

What I did

I tested the theory against everything decoded so far. 34 of 183 references matched the hash of a model’s name, and 149 matched nothing in 1.28 GB of data. The field identifies whole files and cannot select meshes, so placements use the other, proven fields, and this one is recorded as unresolved.

The renderer depends only on fields that are proven.

Windows code, Linux machine

Problem

The native code was written for Windows with Microsoft’s compiler. When I moved to Linux, rewriting it would have invalidated every result proven so far.

What I did

I wrote small compatibility layers for the Windows headers it uses, so the same sources build unchanged on Linux. For the renderer I cross-built with the real MSVC compiler and ran it under Wine. Wine output is treated as proof of correct decoding and drawing, not as proof of identical Windows pixels.

The reference packet fa916943… reproduced exactly, and 13 of 13 behavior tests pass.

Proving the picture is right without saving it

Problem

The usual proof that a renderer works is a screenshot, but game assets are not allowed to leave memory.

What I did

The renderer reads its own frame back from the GPU, projects every object’s placement onto the screen, and checks that the object is actually drawn there. Only counts and a digest of the frame are kept.

Skills

What this project took.

Binary reverse engineering

Decoding undocumented archives, models, skeletons, animation and scenes from raw bytes.

3D graphics

Direct3D rendering, vertex and index buffers, textures, materials and cameras.

Animation math

Quaternions, interpolation, skeleton hierarchies, inverse bind matrices and skinning.

C++ and portability

Native readers built with MSVC, and the same sources on Linux through compatibility layers and Wine.

Static analysis

Mapping 1,204 scripts and 681 imports to understand an engine without running it.

Verification

Reference digests, closure checks and labels that separate proven from guessed.

Python tooling

Probes, parser tests and a desktop asset viewer that works from memory.

Responsible research

Read-only inputs, no exports, no DRM work, and nothing published.

What’s next

The remaining gaps.

  • Skinned character meshes in the world view, which use a different vertex layout.
  • The game’s original materials, shaders and transparency.
  • Pixel evidence from a Windows GPU, beyond what Wine can prove.
  • The full opening sequence, then everything after it.
